A recurring question needs a stable definition

At SupplyBistro, a discussion with my manager clarified that the team wanted AI to help create reusable canned reports internally. A customer asking an AI service a new question on every request raised a different variable-cost problem.

I translated that direction into scope, requirements, planning questions and sprint dependencies. I also presented product direction to C-suite leadership and a prospective client. My contribution was product planning and communication within the team; the executable work here was developed afterward for this portfolio.

The decision in this exercise Store reviewed SQL definitions and run those definitions against the selected period and snapshot. The example makes no runtime AI call.

Agree on what each answer actually measures

Three purchasing questions look related but require different date rules. Treating them as one generic monthly filter would create plausible-looking answers to different questions.

The boundary choices matter. An order due today is not overdue. An order received in October is still open in a September snapshot. A cancellation recorded after that snapshot must not rewrite the earlier result.

Money is stored in integer cents to keep totals exact. Delivery reliability is calculated from all eligible receipts, rather than averaging supplier percentages with unequal denominators. A period with no receipts returns an unavailable rate, rather than a misleading zero.

Repeatability comes with a narrower question set

Reviewed queries work well when questions recur and their definitions are stable. They sacrifice the flexibility of unrestricted natural-language querying. An internal AI drafting workflow could help develop additional reports, but every proposed query would still need a specification and review.

The local Python and SQLite implementation makes that contract easy to inspect without an account or external service. It is an analytical demonstration, not a production backend, and it does not estimate savings without observed usage and cost data.

Validate the definitions before expanding the report list

The existing tests cover meaningful boundaries, including snapshot events, financial reconciliation and empty denominators. Human-readable tables, JSON and charts are generated from the same results.

The next implementation question Which small set of recurring requests would help actual users make decisions? I would confirm that list, inspect the real schema and reconcile representative outputs with a subject-matter reviewer before integration.

This model assumes one currency and one completed receipt or cancellation per order. Partial deliveries, returns, permissions and operational monitoring need explicit treatment in a real implementation.
